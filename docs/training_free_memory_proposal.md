# Training-free Agent Memory：先检查生成产物，再决定机制

## 当前决定（2026-09-12 UTC）

所有本轮运行、排队和后续自动任务已按用户要求取消，核对队列为空；已有 memory 和结果保留。本次不启动新实验。

此前合并 HippoRAG、Mem0、AnchorMem 检索结果的版本是 **ensemble**，不是独立 memory 构建算法，也未证明是能分别接入多数方法的插件。“11/12 领先”仅描述该 ensemble 的已完成本地对照，不作为新的 memory 机制已经成立的证据。相关结果保留为 [第一轮探索记录](memory_research_three_hour_report.md)和[已停止的第二轮记录](memory_improvement_round_two.md)。

下一步先对齐原文、初次抽取、整理后的 memory、retrieval 和 QA，检查同一 Generator Backbone 在不同生成流程下的产物差异。先区分遗漏、误写、整理损失和下游使用失败，再选择具体机制。暂不预设图或 compiler 框架，不以修复 baseline 适配问题作为新贡献。

当前待检验假设是“上下文解释与有损压缩应否分开”，不是已验证算法。后续方案必须是真正单方法输入的可插拔模块，或从原始输入开始的独立完整算法；不再以多方法结果拼接作为主线。分析范围、已有证据和下一步顺序详见 [Generator 与 memory 质量检查计划](generator_memory_quality_review.md)。

## 历史探索与候选（以下不代表当前运行状态或实施计划）

更新日期：2026-09-11。状态：下文完整条件与依赖框架仍是候选；[关系分组原型](relation_memory_experiment.md) 已完成四个任务的 9B 对照，相对相同事实平铺高 1–3 个百分点，不能称稳定提升或 SOTA；来源内主体分组第二版已提交。本文取代原来的 Joint Evidence Memory 训练检索器方案。已完成的产物检查和调查见 [研究迭代记录](memory_research_iterations.md)。

本轮补充：[基于实际失败决定算法方向](memory_failure_mining_and_algorithm_direction.md)。已加入 AnchorMem 两种检索设置的完整单元结果、LightMem 整理前后逐题对照，以及“相同检索文本也会出现不同答案”的归因限制。新原型继续聚焦于持久化记忆组织；PL/system 理论不是替普通分组包装新颖性的工具。

最新授权：自己的方法可以使用 heuristic 或已有组件组合，并在已查看的完整 benchmark 上迭代；不强行新增数据划分。研究定位如实注明探索性开发，不当作未见测试集的泛化证据。此放宽不改变原 baseline 的固定协议，也不允许将标准答案写入构建规则。第一轮覆盖全部六任务，先用 9B 比较相同事实的平铺与分组，不额外调用 Generator。

进一步授权：用户也允许从头设计记忆算法，或改进 retrieval、证据组合、推理和 verifier。因此本文此前“贡献必须仅发生在写入阶段”的限制不再是当前硬约束。研究仍 training-free，优先解释 memory 机制的贡献；若加入查询时推理或校验，必须将它们与记忆改进分别消融，并计入调用成本。当前已提交的关系分组实验不因这一讨论中途改变。

### 已实现但不再作为主方案的 ensemble

研究记录中的 C 是以下 ensemble 操作，而非独立 memory 构建算法：

1. 复用 HippoRAG 已抽取的事实，并建立主体／客体文本到事实编号的索引。索引可供所有问题重复使用，不读取 QA 答案。
2. 固定交错合并 HippoRAG 原文、Mem0、AnchorMem 官方检索和平铺事实，精确文本去重，六任务不切换组合方式。
3. 从最初五条事实沿共享实体找相邻关系，在这些候选中按原问题的固定 embedding 排序，最多追加五条。
4. 使用原 Evaluation Backbone、原最终回答预算和原官方指标作答。图模块没有额外的 LLM 查询或 Generator 调用，但完整流程仍有各 baseline 的原始构建和检索成本。

实现为 `baseline/linked_memory.py` 与 `experiments/run_linked_memory.py`。2Wiki 中，一跳图 58.04% 对应向量追加五条的 51.95%，平均 QA 输入分别为 2,946 和 2,974 token。关系组合题的差距为 40.77% 对 28.24%，但 LoCoMo 上没有图相对向量追加的收益。增加到两跳也没有稳定优于一跳。因此目前优先保留简单连接，不把复杂图结构本身当目的。

此外，已实现一套 HippoRAG 抽取同时提供事实与原文的低构建成本对照，以及路径展示、回取事实原文、额外计划和查询搜索等对照。它们各自的完整状态与失败在研究记录中列出，不按任务择优拼成一个虚构的统一方法。

这还不是已经验证的“改善所有 baseline 的通用插件”：HippoRAG 有显式三元组，其他方法可能只有自然语言。当前完整合并甚至依赖三套构建，必须计入总成本。下一步优先检查能否用一套带来源的事实记忆保留上述收益，而不是先宣称统一替代现有算法。

若借鉴编译器，必须落到三个具体选择：保存什么中间表示、哪些变换不应丢失事实绑定、哪些整理结果可以一次生成后复用。若借鉴系统，则比较提前组织的成本能否被多次读取节省的成本抵消。关系分组只是起点；没有自然语言语义等价证明，不能宣称“编译正确性”或任意信息无损保证。

verifier 可以成为被评测算法的一部分，而不是用来打分的 LLM judge。它的检查范围、是否看答案草稿、额外模型调用和 token 都需明确。若只增加 verifier 即获得同样收益，则贡献可能是读取/回答过程，不应改称记忆表示的收益。最小对照包括原 baseline、加记忆模块、仅加相同 verifier、两者同时加入；无需现在就启动这个更大的实验网格。

最新讨论允许优先考察更有原则的建图：图应保存完整陈述及其适用条件、组合支持与修订关系，而不只是把相似实体连起来。这里的“有原则”是让同一信息保留原则约束构建、整合和更新，不是增加公式或训练边预测器。图表示仍是候选；其具体新颖性尚未成立。

最新收窄：优先检查“共享重复结构、保留每条陈述的关系绑定”的整合操作，代替反复自由改写摘要。它借鉴已有无损关系表示，但自然语言结构对齐如何实现、相对 AnchorMem 和 SodaMem 的差异、净成本收益均未解决，不能称为已提出并验证的新算法。具体产物证据和最近邻比较见 [第四轮研究记录](memory_research_iterations.md#第四轮从真实整合变化收窄到关系保留)。下文条件与依赖框架是背景候选，不表示要把所有组件都实现。

现有 LightMem 的建立后直接评测、Mem0 的官方 SDK 版本都是已接受的实验设置，不能仅凭它们与另一流程不同就判断结果无效。另有 LoCoMo 历史日期锚点的已观察错例，只作事实记录，不据此擅自重跑 Mem0。现在已另行授权 [LightMem 离线整合对照](lightmem_offline_run.md)：复用 memory 副本，不重复抽取。基线流程差异不用于包装新机制的有效性。

原 JEM 的名称与方案由本项目讨论提出，并非已有算法；其中训练检索器的方向不符合要求，已经撤回。本版“条件与依赖”也是待检查的假设，尚未被选定为最终算法。现有论文用于识别先行工作与检验论证，不能因发表场合或流行程度而被当成正确设计。研究顺序是检查真实记忆失败、确定原因、提出最小机制，再验证效果。

## 1. 研究目标与边界

本项目要提出 training-free agent memory 算法，主要对标 LightMem、HippoRAG 2 和 Mem0，同时改善记忆质量与构建、更新、使用效率，并在多个任务和固定 Evaluation Backbone 上检验泛化能力。

所有模型权重保持固定。允许调用 Generator Backbone 完成抽取、整合、压缩、关联和更新；不训练 retriever、reranker、打分器或控制策略，不使用微调、强化学习、蒸馏或监督学习。Training-free 允许模型推理，但不意味着推理判断一定正确。

优先研究持久化记忆的形成和维护；最新授权也允许 retrieval、组合与校验模块。若实际有效操作只发生在读取或回答阶段，应按真实贡献定位，不伪称为写入算法。不训练检索器或其他模型。

统一 backbone、官方数据转换、baseline 默认设置与确定性评测的既有约定继续有效。自己的方法可以尝试明确记录的 heuristic，但不自造评测指标、不添加标准答案规则，不隐藏看过基准后开发的事实。不预设必须建图、禁止压缩或完全弃用生成模型。

## 2. 现有实验说明了什么

完整结果见 [基线结果与失败分析](final_baseline_results_and_failures.md)。以下是研究动机，不能当成新方法的效果证明。

| 已观察到的现象 | 可以支持的判断 | 仍待检查的原因 |
| --- | --- | --- |
| Mem0 的 LoCoMo 9B F1 为 0.537，2Wiki 为 0.436；HippoRAG 2 分别为 0.504、0.519 | 方法在对话记忆和跨文档问答上的优势不同 | 是否与事实脱离上下文、关联表达或更新方式有关 |
| LightMem 的 LoCoMo temporal F1 为 0.128，Mem0 为 0.419 | 时间相关问题值得优先检查 | 时间信息是否在构建时遗漏，还是保留后没有被正确取用 |
| 2Wiki 中三个原文检索方法都召回全部 gold passages 的 286 题，9B F1 接近 | 证据覆盖是重要因素；没有理由优先改弱 evaluator 的能力 | 怎样在构建阶段形成更完整、可复用的记忆单元 |
| Mem0 六任务累计构建约 97,783 秒、1.394 亿 Generator tokens | 当前 SDK 写入成本值得优化 | 它是 ADD-only 流程，不能把该成本称为 UPDATE 重写成本；组成占比仍需检查 |

FactConsolidation-MH 中，三个 evaluator 全错且答案字符串未出现在 top-5 的题数分别为 BM25 76、Dense 76、LightMem 94、HippoRAG 2 77、Mem0 89。这是文字覆盖诊断：字符串不存在不能排除语义等价表达，字符串存在也不能证明全部关系及有效版本已经齐全。因此它不能精确区分构建失败、取用失败和回答失败。

生成式记忆的低分同样不能单独证明压缩删掉了事实。必须查看输入、构建后的记忆、检索内容和预测，才有依据讨论具体原因。

## 3. 核心问题：记忆整合应该保留什么？

以下第 3–7 节中的条件维护、依赖更新和传播机制仍未实现，不是上面 C 的操作说明或已验证贡献。当前结果支持关系组合存在可改善空间，尚未证明这一整套写入框架有效。

工作假设是：记忆整合不仅要保留一句“事实是什么”，还要保留让它能够被正确理解和更新的条件，包括主体、关系、时间、说话者、否定或限定条件，以及它依赖的其他陈述。

例如，以下只是解释机制的例子，不用于生成实验数据：

- “五月住在波士顿”与“八月搬到西雅图”可以同时为真。更新当前住址不应擦掉历史住址。
- “陈说李喜欢茶”不能简化成“陈喜欢茶”，也不能自动等同于李本人的确认。
- “甲的导师是乙”与“乙在丙大学任职”需要保留两条关系；把它们压成“甲与丙大学有关”会丢失关系含义。

由此提出一个待验证的统一原则：

> 整合记忆时保留陈述的适用条件和依赖；新信息到来时，更新受到影响的陈述及其派生记忆。

压缩、关联与更新围绕这个原则展开。它不是对任意自然语言的无损保证；固定 Generator 仍可能误判，必须通过真实错例与消融验证。

## 4. 候选机制：在写入阶段维护有条件的陈述及其依赖

暂不为方法起缩写。先把操作和与先行工作的区别讲清楚，再决定论文命名。

建图的候选单位是“带条件的陈述”，而不只是人名、地名等实体。例如同一个人的两段任职经历，应分别绑定各自公司与时间，避免跨经历拼接。整合结果依赖多条陈述时，还要区分“共同支持”和“各自独立支持”：撤回其中一个来源不一定应删掉所有相关结论。这是已有知识表示与真值维护问题，不是本项目刚发明的操作。是否能在固定模型下以较低成本做好，是需要验证的研究问题。

### 4.1 形成记忆

Generator 读取 benchmark 已转换的原始输入，形成可独立理解的陈述，同时记录输入明确支持的主体、时间、角色和限定条件。相关字段缺失时不补造。

每条生成陈述关联到实际输入的原文片段。这是记忆内容的一部分，用于保留解释条件和检查错误；不建设独立的实验 provenance 系统，不引入数据库或文件哈希。

不要求把所有文本强制变成三元组。如果结构化表达不能容纳原文中的限定，记忆应保留相应文本条件。确切输出格式需要以官方实现和具体错例为依据确定。

### 4.2 整合已有记忆

使用固定、已有的索引查找与新输入相关的记忆，沿用选定基础实现的候选设置；这一检索步骤是写入时寻找待比较对象的配套功能，不训练或重新设计检索器。

固定 Generator 比较新旧陈述及其条件，判断它们是否重复、互相补充、描述不同时期，或在相同适用条件下冲突。整合结果写回持久化记忆，供之后的问题共同使用。

重复内容可以合并；不同条件下成立的事实保留各自条件；明确修订可以更新当前表述并保留历史含义。无法判定的冲突应保持未决，不能凭相似度、模型置信分数或“后写入一定正确”作决定。FactConsolidation 中的新旧顺序必须遵循其官方任务定义，不能推广成所有数据集的规则。

这些语义判断由模型推理完成，不能称为形式化正确性证明。误合并、漏关联和误判修订都是需要记录的可能失败。

### 4.3 保存整合依赖

当一个记忆单元由多个陈述整合而成时，保存它依赖哪些陈述。目的在于让未来更新知道哪些既有记忆受到影响，并保留原始关系，而不是为了在 QA 时运行另一套图搜索算法。

关联描述限于输入支持的关系。系统不在看到评测问题后补写答案路径，也不预先推导任意多跳结论。是否采用显式图作为存储形式属于实现选择，不是已经确定的创新。

### 4.4 更新受到影响的部分

新信息修订某条陈述时，依赖它的整合记忆进入重新整合流程；无关内容继续复用。这项设计的效率假设是减少重复处理旧文本，而不是减少必要输入、缩短生成上限或跳过困难样本。

必须承认两项限制：没有建立的依赖可能导致旧记忆未被更新；依赖过多时，重新整合仍可能很贵。批处理边界、候选数量与调用上限应先依据选定基础实现的官方设置明确记录，再开始实验。本文不臆定“每若干条触发一次”或相似度门限。

这不是追加更多记忆就能自动获得的能力；需要比较依赖维护的额外成本与节省的整合成本。

### 4.5 下游使用

先用现有固定检索流程读取生成的记忆，再由固定 Evaluation Backbone 作答。主要实验中，研究变量是 memory 的内容、组织和更新机制。

检索出的五条记忆不能各自暗中展开成无限多原文。沿用本轮 top-5 控制，并报告实际输入 token 数与记忆单元大小。若新方法仅靠更长的单元获得优势，必须明确报告，不能归因于机制本身。

使用固定 LLM 构建 memory 与用 LLM judge 评测是两回事。效果继续使用官方确定性指标。

## 5. 与已有方法的关系

| 方法 | 已有机制 | 新提案必须检验的差异 |
| --- | --- | --- |
| [Mem0](https://arxiv.org/abs/2504.19413) | 抽取、整合和更新显著事实 | 条件保留和依赖维护是否减少误覆盖，以及是否降低重复更新成本 |
| [LightMem](https://arxiv.org/abs/2510.18866) | 压缩、主题组织、短期记忆与离线整合 | 保留条件的整合是否比现有流程更好；局部更新是否仍有净效率收益 |
| [HippoRAG 2](https://openreview.net/forum?id=LWH8yn4HS2) | 构建关联结构并用于记忆检索 | 写入和维护语义是否有额外价值，不能把关系存储本身称为创新 |
| [A-MEM](https://arxiv.org/abs/2502.12110) | 新记忆触发链接建立及已有记忆演化 | 必须具体比较条件表达、依赖传播和更新范围；“动态关联与演化”已经存在 |

尤其要防止把“事实＋时间＋图＋原文”作为组件列表冒充新方法。A-MEM 已覆盖动态关联与记忆演化，LightMem 已覆盖离线整合，Mem0 已覆盖更新。本提案只是候选机制；对语义条件与依赖的处理是否形成独立贡献，还需核对官方实现和最近邻研究。

这里的 Mem0 更新机制指原论文，不是当前 ADD-only SDK。新增最近邻调查进一步收窄了空间：[StructMem](https://aclanthology.org/2026.acl-short.12/) 已做事件绑定与跨事件整合；[MemForest](https://arxiv.org/abs/2605.23986) 已做局部刷新；[ContextWeaver](https://arxiv.org/abs/2604.23069) 已做推理依赖图；[Dependency-Guided Rollback Repair](https://arxiv.org/abs/2608.10502) 已做依赖指导的局部恢复。“条件图＋局部更新”不能未经进一步区分就成为 novelty 声明。

若最后实现与已有方法只有 prompt 措辞差异，或者仅增加来源链接，就不能声称提出了新的 memory 算法。

## 6. 如何验证

保留现有五个 baseline、六个任务以及 Qwen3.5-9B/4B/2B 三个 evaluator。Generator 使用本轮统一的 Qwen3-30B-A3B-Instruct-2507。所有权重固定，seed 为 42，沿用官方 split、转换和已决定的运行协议。

主要效果指标为 MemoryAgentBench 的 Substring Exact Match、LoCoMo 的官方类别相关 F1、2Wiki 的 answer F1。只有输出能直接对应官方 gold passages 时，才报告可比较的 passage Recall@5 和 Precision@5。不为生成记忆发明 evidence mapping，不从测试答案构造训练标签或写入规则。

没有被评测问题覆盖的能力不作主张。当前静态最终状态评测不能充分验证持续在线更新；若官方任务没有对应检查点，文档只能说明这一证据缺口，不能自行改造数据顺序或生成新的 benchmark。

效率报告构建与更新时间、检索时间、Generator calls/tokens、存储量，以及 evaluator 实际输入长度。现有 baseline 使用不同 GPU，累计 wall-clock 只描述该次运行，不足以单独证明同硬件速度优势。新方法的速度主张需要同硬件、同模型、同输入范围的直接对照。

机制消融分别检查：

1. 保留或移除陈述的适用条件，比较时间、角色与冲突相关错误。
2. 保留或移除整合依赖，比较后续修订后派生记忆是否仍然过时。
3. 相同整合内容采用依赖范围更新或完整重新整合，比较更新成本与结果。

第 1、2 项改变记忆构建，必须分别生成对应 memory；不能复用完整方法的产物假装移除了构建操作。已有 baseline memory 继续复用。消融不增加更强模型或更多最终证据。

以上属于实验设计，尚未运行。没有官方标签支持的中间现象使用可追溯的个案解释，不包装成新的总体指标。

## 7. 下一步与停止条件

先从现有完整结果中检查原始输入、已生成 memory 和错题，确认是否存在条件丢失、错误合并或修订传播失败，并核对基础实现对这些情况已有的处理。个案只用于理解机制，最终效果仍在全部保留任务上评估。

第一轮最小 memory 构建接口已经实现，见[实际运行说明](relation_memory_experiment.md)。它复用已生成事实，既不修改也不重跑已完成的 baseline。下文更复杂的条件/依赖维护仍未实现，不与小原型混称。

已启动的 LightMem 离线对照是单独授权的 baseline 实验，不是新算法。它记录实际 memory 变化，供随后检查整合究竟保留还是破坏了哪些信息绑定。

若确认的主要错误发生在记忆之外，则缩小方法主张。当前授权允许训练自由的检索、上下文组合与额外推理，但必须分别记录其操作和成本，不能将更长输入或更多调用的收益冒充纯写入改进。仍不训练新模型、不用标准答案或逐题规则选取输出。若依赖维护的额外开销超过节省，效率假设不成立。

可以争取的论文故事是：

> 现有记忆系统通过抽取和整合降低历史信息的使用成本，但事实的适用条件和整合依赖可能在变换中丢失。我们研究一种 training-free 的记忆构建与维护机制，在保留这些信息的同时复用未受影响的已有记忆，以改善后续问答并减少重复整合成本。

这是需要实验支持的研究假设，不是已经成立的结论。
