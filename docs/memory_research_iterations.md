# 从真实记忆错误到建图原则：三轮研究记录

当前决定（2026-09-12 UTC）：所有实验已停止，先比较同一 Generator Backbone 下不同 memory 生产流程的产物差异，再决定机制；不预设建图，也不继续多方法 ensemble。详见 [Generator 与 memory 质量检查计划](generator_memory_quality_review.md)。以下是历史审计，个案不代表全量错误占比。

后续实验见 [三小时研究与完整实验记录](memory_research_three_hour_report.md)。本页是较早的产物审计和机制讨论；已有新方法实验结果，后续也已允许无需训练的读取、组合与校验对照。以下保留当时的检查记录，不作为最新运行状态。

更新：2026-09-11。本文记录已经执行的产物检查、原始文献调查和被修正的研究判断。没有新算法的效果结果；没有修改、删除或重跑已有 baseline memory。

## 先说结论

后续实验决策更正：建立后直接评测的 LightMem 和当前 Mem0 官方 SDK 均已被接受，不应仅凭阶段或版本差异称为无效结果。现在额外运行 [LightMem 官方离线整合对照](lightmem_offline_run.md)，只修改副本、不重新抽取。下文保留当时的检查证据，其中关于“缺少阶段”的表述只指相对另一完整流程的区别，不构成必须修复或必须重跑的要求。

可以研究更有原则的建图，但不能把“图更复杂”“加时间字段”“加入依赖边”当成创新。我们真正需要回答的是：**记忆经过抽取、压缩和更新之后，哪些信息仍然必须绑定在一起，才能不改变原来陈述的含义？** 图是表达这些绑定与依赖的工具，研究贡献应在 memory 的形成和维护，而不在训练检索器或加强答题模型。

这轮检查也发现，之前文档对已运行 baseline 的描述过强：LightMem 没有执行官方离线合并阶段；Mem0 使用的当前官方版本是 ADD-only 流程，而不是原论文的增删改流程。已有分数没有被伪造，但不能把这些运行直接解释成完整原论文算法，也不能拿适配问题制造我们新方法的优势。

因此目前保留的是一个研究问题，而不是已经确定的新算法名称。以下记录哪些判断有证据、哪些被否定，以及哪些还需要实验。

## 第一轮：先确认实际运行的是什么

### 检查范围与方法

检查对象是 `final_qwen3_30b_seed42_clean_20260910` 中六个任务的已存储 memory、效率记录和 LoCoMo 全部 1,986 道题。使用 [产物检查脚本](../experiments/inspect_memory_artifacts.py)，通过 SQLite 的只读模式读取现有向量库，输出普通 JSON/JSONL。没有新增实验数据库、文件哈希、自动语义评分或失败分类器。

本轮生成的分析文件位于：

```text
/oscar/scratch/zliu328/agent-memory-analysis/memory_inspection_20260911/

  memory_records.jsonl

```

最后一个文件连接每道官方问题、官方 evidence turn IDs 对应的原始轮次、五个方法的实际 top-5 和三个 evaluator 的预测。1,986 个 case ID 全部唯一；原始引用中有 9 个 evidence ID 未能直接匹配对话轮次，已原样列入 `unresolved_official_evidence_ids`，没有猜测修补。十二个“方法 × 任务”的 memory 导出条数与统计一致；旧产物的 30 个 retrieval cell、90 个 evaluation cell 也再次通过文件与计数验证。它没有为缺失标注补造证据，也没有把检查出来的例子组成新 benchmark。

### LightMem：配置中的 offline 不等于已经执行离线合并

| 任务 | 已存 memory 条数 | 抽取调用 | 离线 update 调用 |

| SH-Doc QA | 3,515 | 406 | 0 |
| MH-Doc QA | 3,730 | 811 | 0 |
| FactConsolidation-SH | 17,663 | 524 | 0 |
| FactConsolidation-MH | 17,663 | 524 | 0 |

| 2WikiMultiHopQA | 6,731 | 950 | 0 |

这不是仅凭一个计数器推断。代码和产物同时支持这个结论：

1. [适配器的 build](../baseline/official.py) 调用 `add_memory`，然后检查非空；没有调用离线队列构建和离线合并。
2. 官方 `offline_update(memory_list)` 默认只将新记录插入向量库；两个触发参数都默认为 `False`。
3. 官方 LoCoMo 构建脚本在 Phase 3 明确调用 `construct_update_queue_all_entries()` 和 `offline_update_all_entries(score_threshold=0.9)`；其说明文档让后续检索读取更新后的目录。[官方复现入口](https://github.com/zjunlp/LightMem/blob/main/experiments/locomo/readme.md)
4. 六个任务记录的 update 调用都是 0，已有记录中也没有非空 update queue。`consolidated=False` 是额外记录状态，不能单独作为是否调用过 update 的判据。

原先“LightMem 全流程已保留”的描述需要撤回。当前结果应标为 **LightMem：离线合并前的适配器运行**。`summarize` 调用同样为 0，但官方 LoCoMo 的额外 summary 阶段可选，不能因此再宣称漏了一项必需步骤。

现有抽取 memory 可以保留。如果以后决定补全协议，候选做法是在独立副本上补官方 Phase 3，再只重做 LightMem 的 retrieval 和 QA；不是重新抽取全部原文。本轮尚未验证这种补执行的兼容性，也没有提交此类作业。LoCoMo 之外的迁移应统一说明采用的算法设置，不能悄悄改变阈值。

### Mem0：当前官方代码和 2025 论文不是同一条写入流程

当前 submodule 是 `mem0ai/mem0@dae67f74f5cc7bf138c7d7d6f9cec5ce4b4373b3`，本轮确认它没有本地未提交改动。

| 任务 | 历史 ADD 次数 | UPDATE 次数 | DELETE 次数 |
| --- | ---: | ---: | ---: |
| SH-Doc QA | 4,222 | 0 | 0 |
| MH-Doc QA | 7,439 | 0 | 0 |
| FactConsolidation-SH | 18,288 | 0 | 0 |
| FactConsolidation-MH | 18,288 | 0 | 0 |
| LoCoMo | 15,150 | 0 | 0 |
| 2WikiMultiHopQA | 19,072 | 0 | 0 |

官方源码 `_add_to_vector_store` 执行 `V3 PHASED BATCH PIPELINE`，使用 `ADDITIVE_EXTRACTION_PROMPT`，只创建新记录。相似历史用于上下文和去重。这些记录与代码一致，不是模型在所有数据集上碰巧都选择了 ADD。

相比之下，[Mem0 原论文 §2.1](https://arxiv.org/html/2504.19413v1#S2.SS1) 描述先抽取、再通过 ADD/UPDATE/DELETE/NOOP 维护记忆的两阶段流程。因此本文中的现有 Mem0 数字必须称为 **Mem0 官方 SDK 的该版本运行**，不能直接证明原论文更新机制的优劣。源文件里仍存在旧 update prompt 或 API 文档，也不能证明运行时调用过它。

这同时修正了效率解释：1.394 亿 Generator tokens 是真实测量，但不能再称为“多轮 UPDATE 重写旧事实的成本”。当前写入仍会读取最近消息和相似 memory，并顺序处理输入；各组成部分的精确 token 占比，现有汇总不足以恢复。

### 第一轮推翻了什么

不能用现在的 LightMem 结果证明离线整合无效，也不能用现在的 Mem0 结果证明删除或覆盖破坏了事实链。两种归因都与实际执行路径不符。

BM25、Dense 和 HippoRAG 2 不因这些发现而自动作废或需要重跑。这里没有给其他方法开出新的全面重跑要求。

## 第二轮：把真实错题分开，不把所有问题都归咎于 memory

以下是逐题诊断案例，不是自动分类后的总体比例。原始标注、实际生成 memory、检索和模型答案均在上述 JSONL 中可查。

### 案例一：memory 保留了时间条件，答题模型没有使用

LoCoMo `conv-26-0` 问 Caroline 何时参加支持小组。官方对话日期为 2023 年 5 月 8 日，证据 `D1:3` 说活动发生在昨天，标准答案是 5 月 7 日。

LightMem 第一条检索结果保存了 5 月 8 日的记录时间以及“昨天参加”的事实。三个 evaluator 都回答了 5 月 8 日。Mem0 此处存成了明确的 5 月 7 日，三个 evaluator 都答对。

能够确认的是：LightMem 这条记忆并没有简单地删掉“昨天”。不能据此称为事实遗漏或抽取失败。把相对时间在写入时解释清楚可能有用，但时间解析已有先行工作，而且新方法不能借此声称提高了模型本身的推理能力。

### 案例二：memory 在写入时使用了错误的时间参照

LoCoMo `conv-26-6` 问 Melanie 计划何时露营。2023 年 5 月 25 日的 `D2:7` 说“下个月”，官方答案为 2023 年 6 月。

Mem0 持久化记录 `49ebdd16-3f8a-462d-b644-e854475902af` 却把它写成约 2026 年 10 月。这不是检索之后才出现的幻觉。另一个持久化条目同时提及 2023 年的对话和 2026 年的计划日期，说明错误已进入可反复取用的 memory。

代码路径中，`generate_additive_extraction_prompt` 没有收到 observation timestamp；`_resolve_dates` 因而把运行当天作为 Observation Date。虽然输入正文含有原始对话日期，模型仍同时收到冲突的时间锚点。官方同步 `add(timestamp=...)` 在这个 SDK 版本中又会拒绝该参数，不能简单声称“补一个参数即可”。

代码行为与错例一致，支持错误时间锚点是原因之一；未经受控重放，不能量化它导致了多少题的错误。修正 historical ingestion 是基线适配问题，不是新建图方法的论文贡献。本轮不改 prompt，不覆盖已有 memory。

### 案例三：官方答案与原始证据本身不一致

LoCoMo `conv-26-5` 的原始 `D2:1` 说上周六参加慈善跑，官方答案却是 5 月 25 日之前的周日。Mem0 输出 2023 年 5 月 20 日，即周六，与原始陈述一致。

这类零分不能简单解释成系统“不记得”。仍保留官方答案和官方得分，不能私自把周日改成周六，不能删题；在误差解释中披露该个案即可。

另一道 `conv-26-1` 的 official evidence 指向展示画作的 `D1:12`，该轮本身并没有提供作画年份。这也说明单个 gold turn 不总是完整可答上下文。因此本轮没有直接把 gold turn 拼接后当作所谓完美 oracle 去跑 GPU 评测。

### 案例四：图中的事实存在，但没有被完整取出

2WikiMultiHopQA `a1cdb240085811ebbd5bac1f6bf848b6` 比较两部电影的导演谁年长。HippoRAG 2 找到了两部电影及 Edith Carlmar，却没有返回 Michael Curtiz 的传记，实际 supporting-passage Recall@5 为 0.75，9B answer F1 为 0。

OpenIE state 中确实保存了 Michael Curtiz 的原文及出生日期三元组。此例不能作为“写入时丢了这个人的出生日期”的证据。它说明有必要区分已存而未取出和根本没存，而不是看到多跳错误就假定缺边。

本轮还检查了 HippoRAG 2 的 6,119 个 OpenIE 文档：没有实体列表为空或三元组列表为空的文档。这个检查只说明列表非空，不意味着每条关系都完整、正确。

### 第二轮得到的研究边界

| 观察到的问题 | 能否直接作为新 memory 方法的动机 |
| --- | --- |
| 必需离线步骤没执行、历史日期锚点错误 | 不能，先作为协议或适配问题处理 |
| 正确信息已经存储但未取出 | 不能直接证明构建失败；也不能借机把项目改成 retriever 研究 |
| 信息已经给出，evaluator 忽略或推理错误 | 不优先优化，不训练更强答题模型 |
| 官方答案或证据标注不一致 | 披露个案，不改标准答案或过滤题目 |
| 原输入支持的条件或关系确实在转换后消失 | 是候选动机，但必须逐题证明，不能从总分猜测 |

## 第三轮：调查最近邻，淘汰只有名称不同的想法

### 事件、时间、分段已经有哪些工作

[StructMem，ACL 2026](https://aclanthology.org/2026.acl-short.12/) 已把事件中的事实与关系绑定，并用跨事件整合形成上层记忆。论文自己指出尚缺显式冲突修订机制。它的主要 LoCoMo 结果使用 LLM judge，不能与我们的 F1 数字直接比较。因此“用事件代替孤立事实”是必须对比的已有设计，不是本项目新发现。

[SimpleMem](https://arxiv.org/abs/2601.02553) 已研究自包含的事实表达和语义压缩；[LycheeMemory V2](https://arxiv.org/abs/2608.12990) 研究分段级写入来降低逐轮调用成本。不能把展开指代、解析时间或增大写入批次当成独立创新，也不能照搬其论文分数作为我们复现正常的判断线。

[Zep](https://arxiv.org/abs/2501.13956) 与 [APEX-MEM，ACL 2026](https://aclanthology.org/2026.acl-long.749/) 已处理时序图或历史版本。因此“记住现在与过去”也不足以单独建立 novelty。

### 依赖与局部更新也不是空白

[MemForest](https://arxiv.org/html/2605.23986v1) 把新写入影响限制到树中需要刷新的部分，并合并重复刷新。因此“只重算受影响节点”不是空白研究题。

[ContextWeaver](https://arxiv.org/abs/2604.23069) 将交互中的推理步骤组织成依赖图，并压缩相关路径。其软件任务设定不同于本项目，但已经覆盖依赖图这一机制，不能只靠换成对话数据声称新颖。

[Self-Correcting Long-Horizon Search Agents](https://arxiv.org/abs/2608.10676) 明确借用真值维护中的依赖修订思想，按树结构回退。[Dependency-Guided Rollback Repair](https://arxiv.org/abs/2608.10502) 又研究错误记忆影响下的局部恢复。这些属于最近邻，即使它们不是我们要做的固定 QA 流程。

[Graph-Native Cognitive Memory](https://arxiv.org/abs/2603.17244) 也提出带修订语义的图记忆架构。本文只将其列为相关预印本；未核实其全部证明与效果，不能用作者声称的形式化保证替代本项目证明。

### 失败分析方面已有的警告

[Useful Memories Become Faulty When Continuously Updated by LLMs](https://arxiv.org/abs/2605.12978) 将整合过程中的条件丢失、错误归组和记忆退化作为研究对象。它支持“抽象并不天然有益”这一警惕，但不能代替我们对自身 memory 的检查，也不能证明我们的基线正在发生同一种故障。

[TrustMem](https://arxiv.org/abs/2606.25161) 用训练改善记忆更新，超出本项目 training-free 边界。[StateAuditor](https://arxiv.org/abs/2608.01619) 重点在答案产生后的检查和修订，也不能拿来当本项目的核心模块。

[MemConflict](https://arxiv.org/html/2605.20926v1) 区分动态、静态和条件冲突，值得用于理解问题。但它的答案和 memory-item 判断采用 LLM 辅助匹配及人工核验，不能直接当成符合本项目“纯确定性评测”的新任务。

### 第三轮的淘汰结论

以下方案单独拿出来都不够：更好的时间 prompt；更大的 memory 单元；分段批量压缩；事实附上原文链接；加一个事件图；局部更新；依赖图回退。也不应把这些组件全部叠在一起，再起缩写包装成统一框架。

## 按最新讨论收敛：怎样的建图才算有原则

### 原则应约束记忆变换，而不是只装饰论文

一个可继续检验的原则是：**变换后的记忆不能把原本属于不同陈述的主体、关系、时间或条件任意拼接；由多条陈述形成的上层记忆，应保留它依赖的支持组合。**

例如，“甲在 2022 年为乙公司工作，2024 年为丙公司工作”包含两段有条件成立的事实。仅把甲、乙、丙、两个年份放进同一团关联中，容易失去谁与哪个年份绑定。再如，两条事实共同支持一个结论，并不意味着每条事实单独支持该结论。这是记忆表达的语义区别，而不是某种 embedding 分数高低。

将多元关系表示为独立的关系实例，是已有的知识表示模式，并非新发明；[W3C 的 n-ary relation 说明](https://www.w3.org/TR/swbp-n-aryRelations/) 给出了明确例子。我们的研究若采用此类结构，应明确承认来源，并在 memory 的形成、压缩或维护操作上提出可检验的差异。

### 候选图里分别存什么

| 对象 | 含义 | 不应混淆成什么 |
| --- | --- | --- |
| 原始观察 | 某人或某篇文档实际说过的内容，以及原生时间/角色 | 模型推断出的世界事实 |
| 带条件的陈述 | 一件事及其主体、关系、明确支持的限定 | 任意独立实体间的相似度边 |
| 整合记忆 | 对若干陈述的可复用组织或概括 | 已被保证正确的新推论 |
| 支持关系 | 某条陈述或某组陈述支持哪个整合结果 | 两段话只是主题相近 |
| 修订关系 | 新观察明确改变了哪个既有陈述的适用范围 | 后写入的内容无条件覆盖旧内容 |

这些类型目前是解释研究问题的候选表示，不是已经确定的实现 schema。所有缺失条件都保持未知；不能自动补一个日期或把未提及当作否定。相似度检索可以沿用官方候选查找入口，但相似度本身不能给支持关系或修订关系盖章。

### 为什么它仍然是 training-free agent memory

固定 Generator 在写入阶段形成陈述、解释关系和提出整合。代码根据实际保存的依赖定位受影响记忆；不训练边预测器、retriever、reranker 或奖励模型。固定 retrieval 与固定 QA 只负责检验最终 memory 是否更有用。

写入阶段可以进行为后续问题通用的解释，例如展开指代；不能读取测试问题和答案后再构造专用路径。不会对每条潜在多跳路径无限预推理，也不能靠把无限原文塞进五条超长 memory 得分。

### 为什么现在还不能声称有新的 principled algorithm

上述原则有两个尚未解决的核心问题。第一，固定 Generator 如何可靠确定条件和支持组合？一个格式正确、带 source ID 的输出仍可能误解原文。第二，依赖记录的成本是否小于减少重复整合带来的收益？没有测量就不能承诺更快。

更重要的是，条件绑定、多元关系、真值维护和局部更新各自都有先行工作。必须说明本项目在哪个具体操作上不同，并通过固定下游的实验排除更长上下文、额外调用或协议修复的影响。不能把“principled”解释成写更多公式，或称一个语义判断流程为正确性证明。

当前可检验的问题是：在固定模型和输入协议下，**保留陈述的组合边界能否改善记忆整合后的复用，并避免无关信息随更新被反复重写？** 这仍是问题，不是已成立的理论或结果。

## 下一轮实验的入口，而不是全面重跑计划

先分开三件事：基线协议差异、已有方法的对照、新机制实验。增加 LightMem 离线阶段是已授权的对照，不是修复无效 baseline；Mem0 官方 SDK 结果继续保留。协议差异或日期锚点调整不能计作新方法的提升。

已有六任务、三个 evaluator 和 deterministic metrics 不变。不删错题，不改官方标签，不引入 LLM judge。本文中的人工检查不构成新评测指标。当前数据主要验证事实与对话记忆，不能据此声称解决长期工具规划或所有在线更新问题。

如果继续到最小机制实现，应先明确基础实现及其官方参数，把变化限制到 memory 形成和维护。第一项对照必须区分“只是换表达方式”与“真的改变了信息绑定”；第二项对照区分“存了依赖”与“依赖确实改变更新范围”。两者都需要对应 memory 构建，不能只换检索时的排序。

此前三轮检查没有占用 GPU。随后已按新的授权启动六任务 LightMem 离线对照及 QA，详见运行记录。该对照修改 memory 副本，原始 memory、retrieval 和 QA 文件保持不动；尚未启动新算法的全量生成。

## 第四轮：从真实整合变化收窄到关系保留

### 已观察到什么，不能推出什么

新的 SH-Doc_QA 产物中，memory `0334782b-1389-41be-a23a-a4d8cd17b1e3` 原本只描述 85 位富人与全球底层一半人口的财富比较。更新后多出“这 85 人占全球人口 0.7%”。检查旧 memory 导出发现，`ae67980a-051f-41bd-a4fc-2cd540ba45ca` 在离线前已经带有这个错误说法。因此这是既有错误在整合中的传播实例，不是离线阶段首次生成该错误的证据。尚未核对它最初来自抽取还是输入文本，也尚未证明它使某道 QA 从对变错。

同一任务另有两个描述欧洲鼠疫时期的条目，在更新后各自吸收另一条的补充内容，两个条目仍然都在。它说明“整合”可能增加重复表述，而不必然压缩条目；不能仅凭有离线调用就宣称压缩或质量提升。

这些检查仅用于解释机制，不引入自动语义标签或新的总体错误率。完整对照仍使用原官方问题与确定性指标。更新前后的具体内容保存在新实验的 `memory_changes.jsonl`。

### 新的候选：共享结构，但不自由重写陈述

本轮更值得研究的操作是：用已有关系表示的共享结构代替反复生成合并摘要。固定 Generator 在建立 memory 时识别一次具体陈述中的参与者、关系和明确限定；每次陈述保留自己的绑定。重复的结构可以共享，但共享参与者并不允许把各陈述的公司、年份、数量重新交叉组合。

说明用的例子：某人 2022 年在甲公司任职，2024 年在乙公司任职。表示可以共享这个人的节点，但两次任职各自保持公司与年份的对应。这个例子不是新 benchmark 或手工规则；它解释为什么“关联实体”与“保留完整关系”不同。

理论参考是已有的 [factorized relational representations](https://www.cs.ox.ac.uk/dan.olteanu/papers/os-sigrec16.pdf)：通过共享重复部分形成紧凑表示，同时保留可展开的原关系。这里借鉴表示原则，不部署数据库，也不声称发明关系分解。表示层的可恢复性只针对已经写入的结构，不保证 LLM 抽取正确，更不保证下游答案正确。

这一候选如果继续，应将研究变量限制在 memory 形成与整合：不让模型反复重写未变化事实，不在读到测试问题后补建答案路径，不更换检索器或 QA。降低重复生成的调用成本、避免把一个陈述的限定复制给另一个陈述，是待验证的假设，不是已经实现的能力。

### 最近邻已经做了什么

- [AnchorMem](https://arxiv.org/html/2604.17377v1) 已经保留不可变原始上下文，以事实为检索锚点，并通过模型生成关联事件。只说“不破坏原文＋建事件图”没有新颖性。候选的区别必须落实为持久化表示的整合操作，而不是检索后取回更多原文。
- [SodaMem](https://arxiv.org/html/2608.08055v1) 已包含事实事件、时间、来源与修订关系。只增加这些字段也不是贡献。
- Factorized representations 本身是成熟工作；把它改名为 memory，同样不够。

因此，当前缺的不是算法缩写，而是一个同时满足三个条件的具体操作：它在自然语言陈述中确实能识别可共享的结构；共享后不会串换各条关系的参与者与限定；结构化和对齐的代价低于节省的整合成本。语义对齐仍可能出错，不能靠未经依据的相似度阈值宣称解决。

### 可证伪的检查顺序

先用本轮官方离线前后对照判断哪些变化影响答案。随后若实现候选，应比较同一份已抽取内容的直接保存、官方合并与结构化整合，以隔离整合操作；完整方法的抽取成本另外计入，不能用复用输入隐藏。固定下游、问题集合和预算，报告实际读入长度。若优势仅来自向 QA 提供更多内容，或收益只是索引查找更快，就不足以支撑新的 memory 算法主张。

现阶段不声称该候选修复了 Oxfam 错误：保存绑定可以限制后续传播，但原始抽取已有的错误仍需承认。也不保证它比所有 baseline 快；首批两个任务的队列构建比 LLM 更新耗时更长，省去更新调用不等于同比例加速整个流程。

## 第五轮：用跨任务分歧定位机制，而不是继续增加数据集

当前评测来自三个 benchmark 家族、六个任务，共 3,386 道问题：MemoryAgentBench 的四任务各 100 题，LoCoMo 1,986 题，以及 HippoRAG 官方复现数据中的 2WikiMultiHopQA 1,000 题。六任务不能表述成六个独立数据集，三个 evaluator 也都属于 Qwen 家族。当前范围适合研究事实与对话 memory，不代表覆盖 MemoryAgentBench 的全部能力，更不代表工具使用、规划和程序性记忆。[MemoryAgentBench 官方说明](https://github.com/HUST-AI-HYZ/MemoryAgentBench/blob/main/README.md)

### 应检查哪些对照

先检查同题方法间的分歧：原始文档或对话中信息是什么，持久化 memory 实际保存什么，检索交给 QA 的内容是什么，最终答案错在哪里。尤其检查两个方向的案例，不能只找支持候选算法的例子。

SH-Doc QA 可用于检查精确事实是否保留；MH-Doc QA 与 2Wiki 可用于检查关联事实是否分别存在、是否共同被取出；FactConsolidation 两任务用于检查新旧或冲突关系；LoCoMo 沿用官方类别检查时间、事件和人物关系。问题类型仅帮助定位检查内容，不替代对原始证据的核实。

LightMem 离线前后是另一项直接对照：检查同题改善和退步，再追到改动过的 memory。多个条目同时变化时不能给某一条操作分配未经验证的因果贡献。答案字符串出现在检索内容中也不等于关系链完整；生成式 memory 没有官方 passage 映射时，不用字符串缺失自动判定信息丢失。

已经查看过的评测错题属于探索性分析，不能再称为从未接触的独立测试证据。若官方提供开发集，应在开发集确定具体实现和设置；不自行切分新数据集，不按错题设置例外，不将评测答案用于构建 memory。现有评测范围与完整官方指标保留，论文如实区分探索与最终验证。

### 新增 baseline 应区分具体解释

优先检查 [AnchorMem](https://aclanthology.org/2026.findings-acl.1736/) 的官方实现与接入条件：它已保留原上下文并建立事实和关联事件，可以检验收益是否仅来自保留原文。其次检查 [StructMem](https://aclanthology.org/2026.acl-short.12/)：它已做事件绑定、时间锚定与跨事件整合，是“保留关系绑定”候选的直接竞争方法。

以上是新增方法的优先顺序，尚未提交它们的生成作业。接入时先核对官方输入、构建流程和预算，沿用项目确定性评测，不照抄论文中的 LLM judge。独立方法间的比较不能替代同一方法有无模块的消融；前者展示差异，后者才更直接检验所改操作。

暂不因为时间类错题存在就扩充一批时间检索方法。只有最终机制确实以时间有效性为核心时，才需要相应时间 memory baseline。目标是用少量最近邻对照把机制说明白，不是增加排行榜行数。
